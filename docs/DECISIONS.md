# Decisions

Recorded bootstrap decisions. Rationale is one line each; revisit only with new device/data constraints.

1. **Android-first** — single test device (Redmi Note 13 Pro 5G); avoids iOS camera-API divergence during MVP.
2. **React Native + TypeScript + Expo** — one codebase, OTA/Go iteration, strict types for clinical code paths.
3. **Expo Go for bootstrap, Expo Development Build later** — no custom native code yet; Dev Build (+ `eas.json`) reserved for Camera2 work.
4. **Kotlin for Android native modules** — Google-recommended, Camera2 samples/interop are Kotlin-first.
5. **Camera2 planned for high-speed capture** — stock Expo camera APIs don't guarantee high-fps/front-camera control; probe first (Phase 1).
6. **MVP = Smooth Pursuit + Horizontal Saccades** — smallest pair covering pursuit + saccadic systems; registry in `src/tests/registry.ts`.
7. **P0.1 probe = Android-only local Expo module, read-only** — `modules/expo-camera2-probe` (Kotlin, autolinked, no app.json plugin entry); TS loads it via `requireOptionalNativeModule` so Expo Go degrades to a Dev-Build hint. No CAMERA permission: verified against AOSP that all six probe keys are basic info, only lens/sensor calibration keys are permission-gated on API 29+.
8. **High-speed verdicts are strict, raw ranges authoritative** — a target fps counts as YES only with a fixed `[fps, fps]` range; matching only a range maximum is reported distinctly as UPPER, never as support.
9. **P1 capture = separate `expo-camera2-high-speed` module, probe stays read-only** — capture validates each mode against live Camera2 data natively (exact size + range match or reject); enumeration reuses the P0.1 probe.
10. **P1 recording = video-only MediaRecorder surface, no preview** — no audio source (no mic permission), app-private cache file; a preview SurfaceView is deferred as desirable-not-required.
11. **P1 dropped-frame counts are documented estimates** — large gap > 1.5×T, missing ≈ Σ(round(dt/T)−1); raw timestamps + session events ship in every report; MediaExtractor sample/duration cross-check is best-effort (nulls, never invented).
12. **P2 MVP camera = FRONT 1920×1080 @ fixed 120fps** — the self-contained mobile test has the user look at the phone display while the camera observes the eyes, so the front camera is the primary eye-tracking candidate. Rear 1080p120 / 720p240 remain technical benchmark modes, not the default clinical-test camera.
13. **~60 Hz CaptureResult cadence is observed Camera2/HAL callback behavior during constrained high-speed batching, not a proven Xiaomi hardware cap** — earlier notes called it a "Xiaomi limitation"; the sustained encoder-side rate (≈116 fps for 120 modes) shows video frames keep flowing, so `onCaptureCompleted` must never be used as the per-video-frame clock. Per-frame timing comes from decoded media PTS.
14. **P2 decode = MediaExtractor + MediaCodec frame-by-frame (no surface), luminance MAD duplicate check, ML Kit ROI behind an isolated interface** — never `MediaMetadataRetriever.getFrameAtTime` as primary; PTS values are labelled encoded/media PTS, never sensor exposure; MAD ≤ 1.5 (0–255, 96×54 Y grid) is a near-duplicate _candidate_ and 1.5–5.0 is low-motion (not a duplicate claim); ML Kit face/eye boxes are feasibility ROIs only (offline evenly-spread subset: 9-frame quick default, 50–100 for validation), never pupil tracking, so OpenCV/custom pupil stages later reuse this decoder untouched.
15. **P2 duplicate gate recalibrated on measured evidence (2026-09-29, garnet)** — the static-scene MAD noise floor (≈1.1–1.5) sits inside the ≤1.5 candidate band, so the pre-device ≤5% candidate rate is not a valid freeze gate as specified; the motion-control response (MAD up to ~14 with an identical anomaly-free 119.5 fps timeline, zero exact-zero MADs in ~2350 comparisons) is the authoritative frozen-frame check. Future fixed gates must sit above the measured noise floor.
16. **P3 pupil stage = small custom CV, no OpenCV, no ML model; baseline `percentile-dark`** — OpenCV would add a large native dependency for morphology/CC boilerplate the prototype implements in ~200 lines of plain SDK code; an ML pupil model would be sophistication without evidence at the feasibility stage. Both candidates share the component/scoring machinery and differ only in the gate (percentile vs contrast-stretch + open); coverage tied within 0.7pp on-device (58.9% vs 59.6%), so the simpler gate with fewer ambiguous outcomes (5 vs 16) is the baseline. The 0.35 confidence gate, 0.05 ambiguity margin, and 50%/20/8 coverage gates are engineering feasibility gates, not clinical thresholds.
17. **P3 eye-side labels stay image-space; mirroring unresolved** — sides echo the ML Kit landmark identity in decoded-frame pixels; `normalizedX` flips meaning if the front-sensor path mirrors. No gaze, degrees, or clinical interpretation may consume these coordinates until mirroring + calibration are explicitly solved (later milestones).
18. **P3.5 preview joins the high-speed session (no CameraX, no second owner)** — the live TextureView surface + the MediaRecorder surface share ONE `CameraConstrainedHighSpeedCaptureSession` (1920×1080 fixed [120,120]); the recorder surface is prepared idle at open so record-start never drops the preview. `cameraOwner` enforces preview XOR one-shot P1/P3 capture. Recording integrity (~120 fps encoded) outranks preview refresh rate.
19. **P3.5 TextureView transform corrects already oriented content** — Android applies sensor orientation, scales into view bounds, and automatically mirrors FRONT preview surfaces. `setTransform` receives a centered CONTENT → DISPLAY cover correction, never the decoded-frame inverse. Native and TS `buildTextureViewMatrix` match; the separate Redmi P2 90° CW DISPLAY → ANALYSIS mapping remains an audit helper, with decoded anatomical side correspondence unresolved. See [Android Camera2 preview](https://developer.android.com/codelabs/android-camera2-preview).
20. **P3.5 mirror is display-only, applied exactly once** — FRONT selfie mode keeps the platform mirror; disabling it adds one compensating flip. Rear previews stay unmirrored. Actual sensor orientation/facing comes from live Camera2 characteristics. Analysis/ROI/normalized coordinates and recordings are untouched. See [OutputConfiguration mirror modes](https://developer.android.com/reference/android/hardware/camera2/params/OutputConfiguration#MIRROR_MODE_AUTO).
21. **P3.5 framing = ~2 Hz ML Kit on displayed snapshots** — `TextureView.getBitmap()` captures transformed DISPLAY content, downscaled to ≤480 px; FAST+landmarks+classification emits direct view fractions, with no aspect guessing or extra inverse/rotation/mirror. Classification gates + 3-sample stabilization are engineering UX gates, not clinical thresholds; no pupil tracking here.
22. **P3.5 READY gate is enforced with a logged override** — the validation Start requires stabilized READY; a “record without gate” path exists only so a framing-classifier miss cannot block the recording-regression check, and its use is recorded in the report.
23. **P4 tracking is per-eye PTS-state-machine over raw P3, full-rate via strict ROI propagation** — `TRACKED / LOW_CONFIDENCE / TEMPORARILY_LOST / BLINK_OR_OCCLUDED / REACQUIRING / LOST` with 500 ms / 2000 ms engineering timeouts on `decodedPtsUs` (never an assumed frame interval); `tracked == accepted raw` (P7 owns filtering), predictions exposed separately, missing stays missing. ML Kit cannot run at 120 fps offline in reasonable time, so 120 keyframes propagate by strict PTS-linear bracketing that never crosses an invalid sample; full-rate native batches run overlay-free with targeted audit overlays after. The hinted second pass (relaxed 0.35 → 0.25 gate, prior-constrained, `p4r_` overlays) only accepts near-prior candidates. Dropout durations are PTS-gap measured; timestamp-gap stats are median-relative so sparse debug sampling is not misread as encoder gaps. All numeric gates are engineering feasibility gates, not clinical thresholds.

24. **Stimulus timing separates planned trajectories, React commits and camera PTS** — use monotonic JS/native clock samples and preserve RTT; current MediaRecorder record-start mapping is explicitly estimated with unknown exposure offset. Never equate it to measured frame exposure or physical display onset. Save raw, versioned cache metadata for future metrics; no calibration/filtering/scoring in this milestone.

25. **Calibration uses stationary target recordings and independent checks** — hold each React-committed target from before recording until after finalization, with a settled guard and clock-bridge uncertainty. Nine per-eye ROI-normalized fit points and five held-out/drift checks produce a guarded affine viewport mapping. Bad coverage/geometry/fixation/ROI stability/validation produces RETRY; mapping and recorded eye exercises cannot consume rejected candidates. No exact exposure/photon-onset claim is added. Numeric gates are engineering choices; real Xiaomi evidence currently rejects the unsupervised run. Contracts/evidence: [Calibration and signals](CALIBRATION_SIGNALS.md).
26. **Signal Processing preserves observations and splits every missing interval** — offline confidence-weighted local linear filtering uses actual decoded PTS; no interpolation, resampling, nominal-interval replacement or derivatives across losses. Reject only weak isolated spikes and preserve rapid sustained motion. Coverage, confidence, reasons and before/after noise proxies accompany all intermediate velocities, without clinical interpretation.
